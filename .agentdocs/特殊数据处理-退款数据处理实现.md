# 特殊数据处理 - 退款数据处理实现说明

## 功能入口

- 前端页面：`#/special-data-processing`
- 页面名称：特殊数据处理
- 模块名称：退款数据处理
- 导航位置：左侧导航栏“高级功能”二级菜单，位于“数据管理”之前。

## 数据字段

`transactions` 表新增字段：

- `finishrefundcheck INTEGER NOT NULL DEFAULT 0`
- 含义：退款检测确认标记。`0` 或 `NULL` 表示尚未确认；`1` 表示已由用户在退款数据处理流程中确认过。

已有 SQLite 数据库通过 `autocoin/database.py` 的轻量迁移自动补列并创建索引。

## API

新增 router：`autocoin/routers/special_data_processing.py`

- `POST /api/v1/special-data-processing/refunds/search`
  - 扫描当前用户未删除、`finishrefundcheck` 为 `0` 或 `NULL` 的疑似退款数据。
  - 返回疑似退款总数、匹配到支出候选的疑似退款数量，以及“一条疑似退款 + 多条支出候选”的结果列表。

- `POST /api/v1/special-data-processing/refunds/confirm`
  - 请求体：`items[]`，每项包含 `refund_id`、`selected_expense_id`、`mark_neutral`。
  - 后端会重新校验当前用户、未删除状态和匹配关系，不盲信前端传入 ID。
  - 提交结果中的疑似退款数据标记 `finishrefundcheck=1`。
  - 只有用户选中的支出候选会标记 `finishrefundcheck=1`。
  - `mark_neutral=true` 时，疑似退款数据及被选中的支出数据方向改为 `neutral`。

## 疑似退款定义

满足以下条件之一，并且 `finishrefundcheck` 为 `0` 或 `NULL`：

- `wechat` 且方向为 `income` 或 `neutral`
- `汇丰PULSE` 且方向为 `income`
- `alipay` 且方向为 `income` 或 `neutral`

所有扫描和处理均按登录用户隔离，并排除 `is_deleted=1` 的交易。

## 匹配规则

通用限制：

- 支出候选必须是同用户、未删除、方向为 `expense`
- 支出时间在疑似退款时间前 0-30 天内
- 支出来源与疑似退款来源一致

来源规则：

- `wechat`：金额完全一致，支付方式完全一致。
- `汇丰PULSE`：金额、支付方式、交易对方完全一致；疑似退款商品名去除末尾 `退款` 或 ` 退款` 后，与支出商品名归一化后完全一致。
- `alipay`：金额、支付方式、交易对方完全一致；疑似退款商品名去除开头 `退款-` 或 `退款- ` 后，与支出商品名归一化后完全一致。

商品名归一化：

- 全角数字、字母和符号转半角。
- 去掉首尾空格，连续空格合并。
- 常见中英文标点统一。
- 英文大小写忽略。
- 不做包含关系、相似度或分词等更宽松匹配。

## 一对多候选与确认语义

- 一条疑似退款数据如果匹配到多条支出数据，搜索结果中全部返回。
- 前端每页最多展示 50 条疑似退款数据，每条疑似退款数据下展示所有支出候选。
- 支出候选按交易时间最近优先、再按 ID 较小排序；默认选中第一条。
- 用户切换分页时，处理勾选状态和支出候选选择状态会保留。
- 用户点击“取消”不会修改任何数据，也不会做标记。
- 用户点击“确认处理数据”后：
  - 提交结果中的疑似退款数据都会标记为 `finishrefundcheck=1`。
  - 如果一条疑似退款有多个候选，只有被用户选中的支出候选会标记为 `finishrefundcheck=1`。
  - 未被选中的支出候选不会标记，后续仍可参与其他匹配。
